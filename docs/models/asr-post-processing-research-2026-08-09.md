# ASR Post-Processing Research - 2026-08-09

This note follows the repo's existing pattern of keeping dated ASR and model research in `docs/models/`.

## Executive summary

For a privacy-first local dictation app, the most evidence-backed architecture is a layered one: keep decode-time customization when the runtime supports it, run deterministic written-form cleanup for punctuation and inverse text normalization (ITN), and then invoke a constrained post-ASR corrector only on likely-error spans. The primary-source literature keeps these concerns separate: contextual biasing focuses on rare words during decoding, while ITN and text formatting focus on converting spoken-form output into clean written text, and post-ASR correction focuses on residual recognition mistakes. [Fast Context-Biasing for CTC and Transducer ASR models with CTC-based Word Spotter](https://arxiv.org/abs/2406.07096) [ASR Language Modeling and Customization - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.12/nemotoolkit/asr/asr_language_modeling_and_customization.html) [Four-in-One: A Joint Approach to Inverse Text Normalization, Punctuation, Capitalization, and Disfluency for Automatic Speech Recognition](https://arxiv.org/abs/2210.15063) [Universal-2-TF: Robust All-Neural Text Formatting for ASR](https://arxiv.org/abs/2501.05948)

For Textify specifically, free-form LLM rewriting is not the safest default. A 2025 study on specialized ASR error-correction models says generic LLM correction raises latency and hallucination concerns, and reports compact seq2seq correction models that outperform neural LM rescoring and generic LLMs while being 15x smaller and 5-40x faster. A separate spoken-to-written conversion paper also warns that LLMs often paraphrase error-free text instead of making minimum edits. [Revisiting ASR Error Correction with Specialized Models](https://arxiv.org/abs/2405.15216) [Recording for Eyes, Not Echoing to Ears: Contextualized Spoken-to-Written Conversion of ASR Transcripts](https://arxiv.org/abs/2408.09688)

For the user's examples, the strongest pattern is "candidate-constrained correction": retrieve likely personal or domain terms, preserve ASR alternatives when available, and only allow replacements that are supported by those candidates or by deterministic formatting rules. That is exactly the direction taken by N-best T5, SoftCorrect, ED-CEC, retrieval-augmented named-entity correction, and RECOVER. [N-best T5: Robust ASR Error Correction using Multiple Input Hypotheses and Constrained Decoding Space](https://arxiv.org/abs/2303.00456) [SoftCorrect: Error Correction with Soft Detection for Automatic Speech Recognition](https://arxiv.org/abs/2212.01039) [ed-cec: improving rare word recognition using asr postprocessing based on error detection and context-aware error correction](https://arxiv.org/abs/2310.05129) [Retrieval Augmented Correction of Named Entity Speech Recognition Errors](https://arxiv.org/abs/2409.06062) [RECOVER: Robust Entity Correction via agentic Orchestration of hypothesis Variants for Evidence-based Recovery](https://arxiv.org/abs/2603.16411)

## What the primary sources say

### 1. Decode-time contextual biasing is still the lowest-hallucination way to fix rare words

The main advantage of contextual biasing is that it changes the decoding process instead of rewriting finished text afterward. NVIDIA's 2024 CTC-WS paper targets rare and new words during decoding and reports improved WER and F-score with lower latency than earlier biasing approaches. NVIDIA's later TurboBias paper extends that idea to CTC, transducer, and attention encoder-decoder models and says it can handle up to 20K key phrases without noticeable speed degradation. [Fast Context-Biasing for CTC and Transducer ASR models with CTC-based Word Spotter](https://arxiv.org/abs/2406.07096) [TurboBias: Universal ASR Context-Biasing powered by GPU-accelerated Phrase-Boosting Tree](https://arxiv.org/abs/2508.07014)

The production-facing NeMo docs are unusually concrete about what this buys in practice. Their context-biasing format explicitly supports multiple spellings and pronunciations for the same term, including abbreviations like `gpu -> gpu / g p u`, compounds like `nvlink -> nv link`, and known model confusions like `nvidia -> n video`. That maps directly onto Textify's `SOTA` versus `soda` problem and onto spoken file-name components such as `md`, `json`, or `tsx`. [ASR Language Modeling and Customization - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.12/nemotoolkit/asr/asr_language_modeling_and_customization.html)

Apple's 2024 contextual-biasing paper is the strongest primary-source evidence that large personal vocabularies can be made practical. It reports up to 71% relative error-rate reduction in personal entity recognition, alongside 20% lower compute time and 85-95% lower memory use for very large biasing catalogues by combining retrieval with vector-quantized biasing. [Optimizing Contextual Speech Recognition Using Vector Quantization for Efficient Retrieval](https://arxiv.org/abs/2411.00664)

### 2. Production systems still treat punctuation, capitalization, and ITN as a separate post-ASR layer

The 2022 Four-in-One paper explicitly models spoken-to-written conversion as a two-stage pipeline: a transformer tagger predicts punctuation, capitalization, disfluency, and ITN tags, and WFST grammars then format the tagged ITN spans. That is important because it treats fragile written forms as constrained formatting, not open-ended rewriting. [Four-in-One: A Joint Approach to Inverse Text Normalization, Punctuation, Capitalization, and Disfluency for Automatic Speech Recognition](https://arxiv.org/abs/2210.15063)

The newer Universal-2-TF paper pushes toward a more neural end-to-end formatter, but it is still framed as text formatting rather than generic editing. Its motivating example is exactly the kind of thing Textify cares about: converting spoken-form text into clean written text with dates, currency, mixed case, and acronyms in the final output. [Universal-2-TF: Robust All-Neural Text Formatting for ASR](https://arxiv.org/abs/2501.05948)

NVIDIA's production docs still ship WFST-based ITN and C++ deployment through Sparrowhawk, and Riva/NIM explicitly run ITN as part of ASR post-processing. That is strong evidence that production teams still prefer constrained grammars for semantically fragile written forms such as numbers, dates, abbreviations, and punctuation-sensitive text. [Deploy to Production with C++ backend - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.07/nemotoolkit/nlp/text_normalization/wfst/wfst_text_processing_deployment.html) [Customizing ASR Models - NVIDIA Speech NIM docs](https://docs.nvidia.com/nim/speech/latest/asr/customization/customization.html)

### 3. Multi-hypothesis correction is one of the most consistent gains after first-pass ASR

N-best T5 is a clean baseline for this idea: instead of correcting only the 1-best transcript, it consumes the ASR N-best list and uses constrained decoding so the correction process stays tied to the ASR decoding space or lattice. The paper's core claim is that richer decoding-space evidence improves correction over a strong Conformer-Transducer baseline. [N-best T5: Robust ASR Error Correction using Multiple Input Hypotheses and Constrained Decoding Space](https://arxiv.org/abs/2303.00456)

FastCorrect 2 makes the same point from a different angle: multiple ASR candidates provide a voting signal that helps both error detection and correction, and the paper reports further WER reductions over single-candidate correction. [FastCorrect 2: Fast Error Correction on Multiple Candidates for Automatic Speech Recognition](https://arxiv.org/abs/2109.14420)

The newer RECOVER paper is useful because it tests the idea on exactly the rare-word and entity failures that matter for dictation. It generates multiple hypotheses from Whisper-small, retrieves relevant entities, and then applies constrained LLM correction plus deterministic verification. It reports 8-46% relative reductions in entity-phrase WER and warns that merge-based fusion can improve entity recall while hurting overall WER through insertion noise; the safer strategies are the selection-based ones that preserve the overall transcript. [RECOVER: Robust Entity Correction via agentic Orchestration of hypothesis Variants for Evidence-based Recovery](https://arxiv.org/abs/2603.16411)

### 4. Specialized post-correctors look safer than generic LLM rewriting for a local product

The 2025 "Revisiting ASR Error Correction with Specialized Models" paper is the clearest current signal here. It argues that generic LLMs are poor fits for practical offline correction because of latency, cost, controllability, and hallucination, and reports that specialized compact seq2seq models trained on ASR error distributions outperform neural LM rescoring and generic LLMs while staying smaller and faster. [Revisiting ASR Error Correction with Specialized Models](https://arxiv.org/abs/2405.15216)

FastCorrect, SoftCorrect, and ED-CEC all support the same product lesson from different directions: correction should be fast, minimum-edit, and focused on likely error locations rather than free-form regeneration. FastCorrect uses edit alignment for fast non-autoregressive correction, SoftCorrect adds soft error detection so it mostly edits suspect tokens, and ED-CEC targets predicted rare-word error positions while injecting a rare-word list as context. [FastCorrect: Fast Error Correction with Edit Alignment for Automatic Speech Recognition](https://arxiv.org/abs/2105.03842) [SoftCorrect: Error Correction with Soft Detection for Automatic Speech Recognition](https://arxiv.org/abs/2212.01039) [ed-cec: improving rare word recognition using asr postprocessing based on error detection and context-aware error correction](https://arxiv.org/abs/2310.05129)

The same pattern appears in phonetic-aware work. PC-MLM masks only low-confidence words from greedy CTC output and predicts replacements using both words and phones, and a 2025 rare-word GER paper says adding phonetic context plus N-best hypotheses reduces over-correction on rare words. Those are directly relevant to `soda -> SOTA` and similar homophone or acronym confusions. [Non-autoregressive Error Correction for CTC-based ASR with Phone-conditioned Masked LM](https://arxiv.org/abs/2209.04062) [LLM-based Generative Error Correction for Rare Words with Synthetic Data and Phonetic Context](https://arxiv.org/abs/2505.17410)

### 5. Retrieval helps most when the correction target is from a known personal or domain vocabulary

The Apple biasing paper shows retrieval is useful before or during decoding. Post-ASR work shows the same pattern after decoding. Apple's result is the strongest decode-time evidence for large personal entity lists, while the 2024 retrieval-augmented correction paper reports 33-39% relative WER reductions on synthetic rare-music-entity test sets without regressing on a general STOP benchmark. [Optimizing Contextual Speech Recognition Using Vector Quantization for Efficient Retrieval](https://arxiv.org/abs/2411.00664) [Retrieval Augmented Correction of Named Entity Speech Recognition Errors](https://arxiv.org/abs/2409.06062)

RECOVER pushes the retrieval idea further by combining exact, fuzzy, and phonetic matching to retrieve a small candidate set before correction, and then verifying every proposed replacement against that list. That "retrieve first, edit second, verify third" structure is the best current primary-source match for Textify's jargon and acronym problem, even though RECOVER itself uses a cloud LLM. [RECOVER: Robust Entity Correction via agentic Orchestration of hypothesis Variants for Evidence-based Recovery](https://arxiv.org/abs/2603.16411)

## Implications for Textify

### Recommended architecture

1. Keep Textify's current deterministic cleanup path, but treat it as the first stage, not the whole answer. The primary-source production stack for written-form cleanup still separates punctuation, capitalization, ITN, and disfluency from later semantic correction. [Four-in-One: A Joint Approach to Inverse Text Normalization, Punctuation, Capitalization, and Disfluency for Automatic Speech Recognition](https://arxiv.org/abs/2210.15063) [Deploy to Production with C++ backend - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.07/nemotoolkit/nlp/text_normalization/wfst/wfst_text_processing_deployment.html)

2. Add a local "spoken-form lexicon" layer before any neural corrector. This layer should own things like `dot`, `slash`, `underscore`, common file extensions, explicit acronym verbalizations, and personal vocabulary entries with alternate pronunciations. This is an inference from how NeMo models speech hints and context-biasing spellings, and from the fact that production ITN systems still use constrained grammars for fragile text forms. [ASR Language Modeling and Customization - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.12/nemotoolkit/asr/asr_language_modeling_and_customization.html) [Customizing ASR Models - NVIDIA Speech NIM docs](https://docs.nvidia.com/nim/speech/latest/asr/customization/customization.html)

3. If the active ASR runtime can expose alternatives, preserve them. N-best or multi-hypothesis evidence is one of the most repeated wins in the primary sources, and it is especially valuable for homophones, acronyms, and deleted rare words. [N-best T5: Robust ASR Error Correction using Multiple Input Hypotheses and Constrained Decoding Space](https://arxiv.org/abs/2303.00456) [FastCorrect 2: Fast Error Correction on Multiple Candidates for Automatic Speech Recognition](https://arxiv.org/abs/2109.14420) [RECOVER: Robust Entity Correction via agentic Orchestration of hypothesis Variants for Evidence-based Recovery](https://arxiv.org/abs/2603.16411)

4. Invoke a compact local corrector only when a span looks risky. The literature repeatedly tries to avoid editing already-correct tokens: SoftCorrect uses soft error detection, PC-MLM masks low-confidence words, and ED-CEC corrects predicted error positions only. The practical product inference is to gate correction on low confidence, suspicious vocabulary hits, or explicit user-vocabulary overlap instead of always rewriting the whole sentence. [SoftCorrect: Error Correction with Soft Detection for Automatic Speech Recognition](https://arxiv.org/abs/2212.01039) [Non-autoregressive Error Correction for CTC-based ASR with Phone-conditioned Masked LM](https://arxiv.org/abs/2209.04062) [ed-cec: improving rare word recognition using asr postprocessing based on error detection and context-aware error correction](https://arxiv.org/abs/2310.05129)

5. Prefer a specialized local seq2seq or focused non-autoregressive corrector over a general LLM rewrite pass. The strongest direct evidence for that choice is the 2025 specialized-model paper, backed by the older FastCorrect and SoftCorrect lines of work. [Revisiting ASR Error Correction with Specialized Models](https://arxiv.org/abs/2405.15216) [FastCorrect: Fast Error Correction with Edit Alignment for Automatic Speech Recognition](https://arxiv.org/abs/2105.03842) [SoftCorrect: Error Correction with Soft Detection for Automatic Speech Recognition](https://arxiv.org/abs/2212.01039)

### Concrete model choices

The best fit for Textify is a compact `N-best T5` or `ECLM`-style seq2seq corrector if Textify can preserve multiple hypotheses, or a `SoftCorrect` or `PC-MLM`-style focused corrector if Textify only keeps 1-best text plus confidence-like signals. That recommendation is an inference from the cited papers' model families and objectives, not a benchmarked Apple-Silicon claim. The evidence-based part is that T5-family N-best correction, specialized seq2seq correction, soft-detection correction, and phone-conditioned correction are all established primary-source approaches for minimum-edit post-ASR repair. [N-best T5: Robust ASR Error Correction using Multiple Input Hypotheses and Constrained Decoding Space](https://arxiv.org/abs/2303.00456) [Revisiting ASR Error Correction with Specialized Models](https://arxiv.org/abs/2405.15216) [SoftCorrect: Error Correction with Soft Detection for Automatic Speech Recognition](https://arxiv.org/abs/2212.01039) [Non-autoregressive Error Correction for CTC-based ASR with Phone-conditioned Masked LM](https://arxiv.org/abs/2209.04062)

If Textify later adds a runtime with first-class hotword biasing, decode-time customization should stay ahead of post-correction for user dictionaries because it has a better hallucination profile. The strongest currently cited options are NeMo's CTC-WS and related TurboBias line, plus Apple's retrieval-assisted contextual biasing. [Fast Context-Biasing for CTC and Transducer ASR models with CTC-based Word Spotter](https://arxiv.org/abs/2406.07096) [TurboBias: Universal ASR Context-Biasing powered by GPU-accelerated Phrase-Boosting Tree](https://arxiv.org/abs/2508.07014) [Optimizing Contextual Speech Recognition Using Vector Quantization for Efficient Retrieval](https://arxiv.org/abs/2411.00664)

### What this means for Textify's current `whisper.cpp` path

The official `whisper.cpp` header already exposes `initial_prompt`, `prompt_tokens`, `suppress_regex`, `grammar_rules`, a `logits_filter_callback`, beam-search parameters, token timestamps, and decode thresholds such as `entropy_thold`, `logprob_thold`, and `no_speech_thold`. That means the current runtime can already support light prompt conditioning, token suppression, grammar-constrained decoding experiments, and confidence-gated post-processing. [whisper.cpp `whisper.h`](https://github.com/ggml-org/whisper.cpp/blob/master/include/whisper.h)

In the cited header, I did not find a first-class hotword or context-file API comparable to the NeMo and sherpa documentation. My inference is that advanced per-user vocabulary support is more naturally implemented in Textify today as post-processing plus retrieval, unless the app adopts a different ASR runtime or extends `whisper.cpp` itself. [whisper.cpp `whisper.h`](https://github.com/ggml-org/whisper.cpp/blob/master/include/whisper.h) [ASR Language Modeling and Customization - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.12/nemotoolkit/asr/asr_language_modeling_and_customization.html) [Hotwords (Contextual biasing) - sherpa docs](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)

## Handling the user's example failures

### `soda` versus `SOTA`

The evidence-backed path is not "let an LLM rewrite the sentence until it looks plausible." The safer pattern is: store `SOTA` in a local vocabulary with alternate verbalizations, bias or retrieve it when relevant, and only replace `soda` if the ASR alternatives, phonetic context, or local vocabulary evidence support the acronym. That combines the strengths of contextual biasing, phonetic-aware correction, and minimum-edit constrained decoding. [ASR Language Modeling and Customization - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.12/nemotoolkit/asr/asr_language_modeling_and_customization.html) [Non-autoregressive Error Correction for CTC-based ASR with Phone-conditioned Masked LM](https://arxiv.org/abs/2209.04062) [LLM-based Generative Error Correction for Rare Words with Synthetic Data and Phonetic Context](https://arxiv.org/abs/2505.17410)

### `fixes dot md` versus `fixes.md`

This belongs first to deterministic formatting and ITN, not to semantic rewriting. Production ASR stacks still treat ITN and punctuation-sensitive formatting as dedicated post-processing, and NeMo's context-biasing examples explicitly handle alternate spoken spellings for abbreviations and compounds. The product inference is that file names should be handled by protected-span rules plus a small extension lexicon before any general corrector runs. [Four-in-One: A Joint Approach to Inverse Text Normalization, Punctuation, Capitalization, and Disfluency for Automatic Speech Recognition](https://arxiv.org/abs/2210.15063) [Deploy to Production with C++ backend - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.07/nemotoolkit/nlp/text_normalization/wfst/wfst_text_processing_deployment.html) [ASR Language Modeling and Customization - NVIDIA NeMo docs](https://docs.nvidia.com/nemo-framework/user-guide/24.12/nemotoolkit/asr/asr_language_modeling_and_customization.html)

### `to` versus `two`

This is where candidate-constrained correction helps most. If the runtime can expose N-best hypotheses or alternate decodes, use them; if it cannot, use local formatting clues and only limited post-correction on low-confidence spans. The N-best and focused-correction papers consistently support using more evidence while reducing unnecessary edits. [N-best T5: Robust ASR Error Correction using Multiple Input Hypotheses and Constrained Decoding Space](https://arxiv.org/abs/2303.00456) [FastCorrect 2: Fast Error Correction on Multiple Candidates for Automatic Speech Recognition](https://arxiv.org/abs/2109.14420) [SoftCorrect: Error Correction with Soft Detection for Automatic Speech Recognition](https://arxiv.org/abs/2212.01039)

## Failure modes and risks

Generic LLM correction can over-edit fluent but correct text. That is a repeated warning in both the specialized-model paper and the contextualized spoken-to-written paper, and it is the main reason not to default to full-sentence rewriting in Textify. [Revisiting ASR Error Correction with Specialized Models](https://arxiv.org/abs/2405.15216) [Recording for Eyes, Not Echoing to Ears: Contextualized Spoken-to-Written Conversion of ASR Transcripts](https://arxiv.org/abs/2408.09688)

Entity-focused multi-hypothesis fusion can improve the target term while hurting the surrounding transcript. RECOVER explicitly reports this trade-off for merge-style fusion methods, which is why selection-based strategies are safer when overall dictation quality matters more than maximum entity recall. [RECOVER: Robust Entity Correction via agentic Orchestration of hypothesis Variants for Evidence-based Recovery](https://arxiv.org/abs/2603.16411)

Biasing without good filtering can become too aggressive on large vocabularies. Both Apple's retrieval paper and the contextual spelling-correction papers are built around the idea that the candidate list must be filtered before correction or biasing. [Optimizing Contextual Speech Recognition Using Vector Quantization for Efficient Retrieval](https://arxiv.org/abs/2411.00664) [Towards Contextual Spelling Correction for Customization of End-to-end Speech Recognition Systems](https://arxiv.org/abs/2203.00888) [A Light-weight contextual spelling correction model for customizing transducer-based speech recognition systems](https://arxiv.org/abs/2108.07493)

## Practical recommendation for Textify

The best near-term Textify architecture is:

1. Keep the existing deterministic punctuation and cleanup pipeline.
2. Add a local spoken-form lexicon for acronyms, file extensions, and user vocabulary with alternate pronunciations.
3. Preserve ASR alternatives when available.
4. Run a focused local corrector only on suspicious spans.
5. Constrain replacements to retrieved candidates or ASR-supported alternatives.

That recommendation is an inference from the primary sources above. The evidence-based reason for it is that the best reported gains come from combining constrained formatting, contextual biasing or retrieval, multi-hypothesis evidence, and focused minimum-edit correction rather than unconstrained transcript rewriting. [Four-in-One: A Joint Approach to Inverse Text Normalization, Punctuation, Capitalization, and Disfluency for Automatic Speech Recognition](https://arxiv.org/abs/2210.15063) [N-best T5: Robust ASR Error Correction using Multiple Input Hypotheses and Constrained Decoding Space](https://arxiv.org/abs/2303.00456) [Revisiting ASR Error Correction with Specialized Models](https://arxiv.org/abs/2405.15216) [Optimizing Contextual Speech Recognition Using Vector Quantization for Efficient Retrieval](https://arxiv.org/abs/2411.00664) [RECOVER: Robust Entity Correction via agentic Orchestration of hypothesis Variants for Evidence-based Recovery](https://arxiv.org/abs/2603.16411)
